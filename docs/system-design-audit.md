# Junk It Out system design audit

## Scope

Inspection of the local working tree on 2026-10-23, followed by a narrow code fix removing request-time schema DDL from three complaint-related handlers. No database, payment provider, SMS provider, production service, deployment, or external endpoint was contacted. The working tree had numerous pre-existing changes; those were preserved. Findings describe the current checkout and are not a certification of production behavior.

## Confirmed findings

| Priority | Evidence and impact | Action | Dependencies / approval |
|---|---|---|---|
| P1 — fixed | `app/api/admin/sync-schema/route.ts` exposed schema alteration from an authenticated `GET`; the same `ALTER TABLE` was also run from admin complaint `GET` and complaint submission `POST`, including the public contact-submission path. Normal requests could execute DDL, and the admin GET could be triggered by a top-level navigation with a `SameSite=Lax` cookie. | Removed request-time DDL from all three handlers. The schema diagnostic is now read-only; complaint routes use normal Prisma operations. Added tests asserting no raw SQL write call. Schema changes belong in reviewed migrations. | No migration was run. If the local database schema is stale, a separately approved migration is needed. |
| P1 — unresolved, owner review | `app/api/auth/admin-login/route.ts` updates an existing allowlisted account’s role/profile during login and runs a broad `user.updateMany` that demotes every ADMIN/SUPER_ADMIN whose phone is outside a hard-coded pair. This can change unrelated roles during login. | Do not change the allowlist or mutate real accounts without the owner deciding how existing administrators should be managed. Replace login-time bulk role mutation with an explicit, reviewed provisioning/revocation process. | Owner approval required; production allowlist and records were not accessed. |
| P1 — unresolved | `app/api/admin/stats/route.ts` sets `totalCustomerPayouts` equal to `totalRevenue`. Revenue comes from captured payments, while customer payouts are represented by `Settlement` rows. The dashboard can therefore show a financially misleading metric. | Owner/product must define whether the figure means accrued settlements, approved payouts, or completed transfers; then aggregate the corresponding state and add metric tests. | No schema migration if existing settlement states suffice; finance/product approval required. |
| P1 — partially mitigated; durable recovery unresolved | `app/api/payments/webhook/route.ts` commits captured payment/order state before dispatch. A duplicate capture event previously returned before dispatch, and dispatch swallowed failures, so the provider could receive a success response while the order remained undispatched. | Captured-event redelivery now retries dispatch, and dispatch failures propagate so the webhook can return 500. This supports provider retry and the existing customer reconciliation path after restart. It is not durable if the provider stops retrying or no customer reconciliation occurs; a transactional outbox/dispatch state remains the robust fix. | Outbox/dispatch state likely requires a schema migration and owner approval for retry/agent notification semantics. No provider was contacted. |
| P1 — partially mitigated; refund recovery remains bounded | Refund route atomically claims Payment/Order and creates a RefundAttempt before a single provider POST, uses Razorpay's documented `X-Refund-Idempotency` support with a stable payment-derived key, and never repeats the POST for in-flight local states. Timeouts and local persistence failures remain pending for read-only provider-list reconciliation; signed refund webhooks reconcile pending/processed/failed states transactionally with deterministic event IDs. Provider success is accepted only when evidence matches payment ID, full amount, currency, marker, and supported provider status. | RefundAttempt durably stores the provider refund ID and current attempt state; RefundAttemptEvent stores sanitized request, webhook, and reconciliation observations. The supplied tables do not have dedicated idempotency-key/provider-status columns or Payment/Order foreign keys, so request metadata is in event JSON and the two identifiers remain scalar. Only one full refund is supported. A request never accepted by Razorpay still requires manual review; the code does not blindly POST again. The supplied DDL was mirrored in Prisma, but no remote database comparison was performed. | No migration was run. Partial-refund semantics and operator policy still require owner approval. |
| P1 — unresolved | Settlement rows can be marked `APPROVED` or `READY_FOR_PAYOUT` by `app/api/admin/settlements/route.ts`, but no transfer/payout integration was found. Status can be mistaken for money delivered. | Name states precisely and implement transfer tracking/reconciliation only after product and finance approval. | Finance/owner approval and provider credentials/integration required; none were used. |
| P2 — unresolved | `lib/auth/otp.ts` stores send/verify limits in per-process `Map`s. Restarting or routing requests to another instance resets or bypasses limits; map entries also have no general cleanup. | Use shared, bounded rate-limit storage and trust client IP only from configured proxy headers. | Requires shared storage/configuration and abuse-policy approval. |
| P2 — unresolved | `lib/realtime.ts` keeps the broadcaster in process memory. SSE subscribers on another instance will not receive events; restart loses subscriptions. | Adopt a shared pub/sub or durable event mechanism if multi-instance deployment is required. Validate actual deployment topology first. | Infrastructure decision required; no deployment topology was changed. |
| P2 — unresolved | The Prisma schema uses free-form strings for roles, order states, payment states, and agent states. Invalid values can be persisted despite transition validation in application code. | Plan enum/check constraints with a data audit and backward-compatible migration; do not migrate as part of this review. | Migration and owner approval required. |
| P2 — unresolved | Some reporting/admin list paths fetch unbounded result sets; the CSV report loads all orders with customer/address relations. Large datasets can increase latency and memory use. | Add bounded pagination/streamed exports and query-plan tests; confirm expected report semantics before changing API contracts. | No migration initially; API compatibility/product approval and representative performance data needed. |
| P2 — unresolved | Admin/customer JWT role claims are not refreshed against the database on every request; agent tokens have a `tokenVersion` check. Role changes may not revoke existing admin/customer tokens until expiration. | Define revocation/session requirements and add a targeted server-side check or revocation version without weakening OTP or role checks. | Session policy/owner approval; performance impact should be measured. |

No P0 finding was confirmed in the inspected local code. This does not establish that the system is secure or production-ready.

## Improvements implemented

- Made `GET /api/admin/sync-schema` read-only and separated unauthenticated `401` from signed-in non-admin `403`.
- Removed the same raw DDL from admin complaint listing and complaint submission.
- Added route tests with database delegate stubs. They check authorization and confirm these handlers do not execute raw SQL writes.
- Updated payment webhook dispatch so a duplicate captured event retries dispatch and dispatch failures propagate to the webhook caller; added a pure test for duplicate delivery and retry after a simulated local failure.
- Hardened full Razorpay refunds using current status columns only: atomic claim/finalization, documented provider idempotency header, no POST retry for in-flight states, read-only reconciliation, and signed refund webhook handling. Added mocked refund workflow tests. No refund ID is persisted because the schema has no suitable field.
- No schema, records, roles, credentials, deployment, or integration calls were changed.

Tests that write database fixtures were not run. No database migrations or seeds were part of verification. A production build was not run because the root build script invokes Prisma generation and the Next build may execute route code; no build-time database behavior was verified.

## Approval and remaining work

- Owner review is needed before altering admin provisioning/allowlist behavior or defining payout accounting states.
- Refund-attempt history, durable provider refund IDs, partial refunds, and automatic recovery after a provider request was never accepted still require an approved schema migration and operator workflow.
- Shared rate limiting/event transport needs an explicit infrastructure decision.
- Durable payment webhook delivery and refund reconciliation need schema/provider workflow approval. The webhook retry behavior currently has pure local tests only.
- Do not rerun the local dashboard fixture creator; the dashboard already contains fixtures.
